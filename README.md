# SETA — корпоративный Telegram-ассистент руководителя

Система управления рабочим временем, встречами, решениями, поручениями и контролем
исполнения. Telegram — интерфейс, вся логика на защищённом сервере.

**Статус:** блоки 1 и 2 из 6 завершены и проверены · 31 августа 2026

---

## Зачем это

Рабочий день руководителя разорван между Telegram, звонками, встречами, устными
поручениями и памятью ассистента. В результате часть поручений теряется, сроки
помнит один человек, а результат проверяется тогда, когда о нём случайно вспомнили.

Система замыкает один управленческий цикл:

```
Запрос → Свободное окно → Встреча → Решение → Поручение →
Исполнитель → Срок → Контроль → Проверка → Результат → Сводка руководителю
```

Ценность не в количестве функций, а в том, что этот круг замыкается без ручного труда.

## Что уже работает

### Регистрация — три пути, ни одного вручную заведённого сотрудника

| Путь | Как | Роль |
|---|---|---|
| Ссылка отдела | Администратор отправляет ссылку в чат отдела | «Сотрудник» выдаётся сразу |
| Свободная заявка | Человек сам открывает бота и выбирает роль | Подтверждение одним касанием |
| Личное приглашение | Одноразовая ссылка под конкретного человека | Любая роль сразу |

Завершается подтверждением номера телефона штатной кнопкой Telegram.
Повышенные роли через многоразовую ссылку не выдаются никогда — её могут переслать.

### Права: четыре уровня контроля

**Роль** (кто ты) → **право** (что разрешено) → **область** (над какими записями) →
**проверка конкретной записи** (я автор? исполнитель? мой отдел?).

Шесть ролей, 28 прав, 69 связок с областями видимости. Сотрудник физически не может
открыть чужое поручение, даже зная его точную формулировку. Администратор управляет
системой, но не видит содержание встреч и поручений руководства.

### Индикатор доступности руководителя

Одно касание — и сотрудники видят, что руководитель принимает прямо сейчас:

🟢 принимаю 30 мин / 1 час / до конца дня  ·  🌙 поздний приём  ·  🟡 занят  ·  🔴 не беспокоить

У состояния всегда есть срок: по его истечении индикатор снимается сам. Режим
«поздний приём» открывает окна после конца рабочего дня — тогда, когда руководитель
к этому готов, а не постоянно.

Рабочий день по умолчанию **09:00–19:00**, обед 13:00–14:00, буфер между встречами
15 минут, выходные — суббота и воскресенье. Настраивается по каждому человеку.

### Администрирование прямо в Telegram

Заявки на регистрацию · сотрудники и роли · отделы · ссылки-приглашения ·
журнал действий. Отдельный веб-интерфейс появится в блоке 5.

### Поручения и контроль исполнения

Создание за четыре шага: кому, что сделать, срок, приоритет. Срок пишется словами —
«до пятницы», «через 3 дня», «05.09», «5 сентября 15:00».

```
Новое → Принято → В работе → На проверке → Выполнено
                      ↑            │
                      └────────────┘  возврат на доработку
```

Проверка качества включается сама для приоритетов Высокий и Критичный. Возврат
на доработку требует комментария — «переделай» без причины бесполезно. Возвраты
считаются: это и есть настоящий показатель качества работы, а не число закрытых задач.

Срок исполнитель не двигает сам: он просит с обоснованием, автор решает. Каждое
продление сохраняется — через месяц видно, кто хронически сдвигает сроки.

### Напоминания и эскалация

| Момент | Кто получает |
|---|---|
| За 48 часов, за 24 часа, в день срока | Исполнитель |
| Срок прошёл | Статус «Просрочено», исполнителю |
| +1 день | Начальник отдела |
| +3 дня или Критичный | Ассистент |
| Руководителю | Только в сводке — поштучно никогда |

Исключение одно: поручение с флагом «на личном контроле» — о его просрочке
руководитель узнаёт немедленно.

Защита от лавины сообщений встроена: повторная обработка события не создаёт
второе уведомление, тихие часы сдвигают доставку до утра, четыре и более
обычных сообщений уходят одним.

### Журнал аудита

Только добавление записей. Хранит «было / стало», причину и настоящего автора —
включая случаи, когда ассистент действует по поручению руководителя.

## Технологии

| Слой | Что | Почему |
|---|---|---|
| Бот | aiogram 3 | Асинхронный, зрелый, лучшая поддержка сценариев Telegram |
| API | FastAPI + Pydantic 2 | Валидация и автодокументация из коробки |
| База | PostgreSQL 16 | Задача реляционная: интервалы, права, аудит, полнотекстовый поиск |
| Кэш и очередь | Redis 7 + ARQ | Планировщик, блокировки, удержание слотов |
| Схема | SQLAlchemy 2 + Alembic | Миграции версионируются, ручные правки базы запрещены |
| Интерфейс | React + TypeScript (блок 5) | Стандарт для Telegram Mini Apps |
| Запуск | Docker Compose | Переезд к любому провайдеру — копирование папки и дампа |

**Firebase рассматривался и отклонён:** задача реляционная, аудит требует транзакций,
ядро продукта — постоянно работающий планировщик, полнотекстового поиска нет,
и уход с платформы означал бы переписывание. Обоснование целиком —
в [`agent/DECISIONS.md`](agent/DECISIONS.md), решение Р-02.

## Запуск

```bash
cd seta
cp .env.example .env      # если .env ещё нет
```

В `.env` заполните две строки:

```
BOT_TOKEN=токен_от_BotFather
BOOTSTRAP_ADMIN_TELEGRAM_ID=ваш_числовой_id
```

Свой Telegram ID даёт бот `@userinfobot` либо команда `/id` у своего бота.

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d
docker compose logs -f bot
```

Откройте своего бота и отправьте `/start`. Подробности — в [`seta/README.md`](seta/README.md).

### Проверка

```bash
cd seta
docker compose -f docker-compose.yml -f docker-compose.dev.yml \
  run --rm --no-deps migrate python scripts/smoke_block1.py
docker compose -f docker-compose.yml -f docker-compose.dev.yml \
  run --rm --no-deps migrate python scripts/smoke_block2.py
```

**34 и 52 сценария.** Проверяются не только успешные пути, но и отказы: обращение
к чужим данным, повышенная роль по пересланной ссылке, перенос срока назад,
закрытие поручения мимо проверки. Ожидается `Ошибок: 0`.

## Для ИИ-агентов

Любой агент, подключившийся к репозиторию, начинает с [`AGENTS.md`](AGENTS.md) —
там порядок чтения и правила проекта. Папка `agent/` содержит весь контекст,
необходимый, чтобы продолжить работу без пересказа истории.

Главные правила: система считает — ИИ объясняет; роль, выбранная себе самому, —
это заявка; право не равно доступу; секреты только в `.env`.

## Безопасность

- Токен бота, ключ ИИ и пароль базы живут только в `.env`: файл не попадает
  ни в репозиторий, ни в образ.
- Вебхук защищён HTTPS и секретным токеном, данные Mini App проверяются на сервере.
- Каждое критичное действие пишется в неизменяемый журнал аудита.
- Права проверяются на уровне отдельной записи, а не только по роли.
