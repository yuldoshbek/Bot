# Архитектура для агента

Краткая техническая карта. Полный документ для людей — `Архитектура SETA.html`.

## Слои

```
Telegram (бот + Mini App)
      ↓
Caddy: HTTPS, секретный токен вебхука, лимиты частоты
      ↓
Core API (FastAPI) — модули: auth, users, departments, calendar,
      meetings, tasks, notifications, files, analytics, ai, admin, audit
      ↓
PostgreSQL 16 (источник истины)   Redis (очередь, блокировки, кэш, удержание слотов)
      ↓
Фоновые обработчики: планировщик, рассыльщик, ИИ, индексатор
      ↓
Наружу: Telegram Bot API, OpenAI API, резервные копии
```

**Правило вебхука.** Обработчик делает три вещи: сохраняет событие, ставит в
очередь, отвечает «принято». Ничего долгого внутри запроса — Telegram ждёт секунды.

**Идемпотентность.** У каждого события свой идентификатор. Повторная доставка от
Telegram или повторный запуск обработчика не создают второе уведомление.

## Структура кода

```
seta/
  app/
    core/       config, db, redis, timeutil, dates (разбор сроков), text (экранирование)
    models/     base, enums, org, user, rbac, schedule, task, notification,
                audit, error, meeting, decision, document
    services/   rbac, registration, availability, tasks, deadlines, notifications,
                bootstrap, audit, health, slots, meetings, attendance, quotas,
                decisions, documents, indexer, search, briefing, export, analytics
    bot/        loader, run, utils, middlewares/auth, handlers/*, keyboards/*
    workers/    runner.py: четыре цикла — доставка, сроки, встречи, документы
    api/        main.py: вебхук + /health, health_page: страница состояния
  migrations/   версии схемы (Alembic), шесть миграций
  scripts/      smoke_block1..4, smoke_hardening, stress_test,
                make_admin, backup.sh, restore.sh
```

Подробное назначение каждого файла — `STRUCTURE.md` в корне репозитория.

## Модель данных

**39 таблиц.** Блоки 1–4 реализованы полностью, плюс блок укрепления.
Модели и миграции сверены: расхождений нет ни по таблицам, ни по уникальным
ограничениям, ни по индексам.

Блок 1 — ядро:

| Таблица | Назначение |
|---|---|
| `organizations` | Организация. `organization_id` заложен везде, хотя она пока одна |
| `departments` | Дерево подразделений, начальник отдела |
| `users` | Сотрудник: связь Telegram ID ↔ корпоративная личность, отдел, статус, часовой пояс |
| `invites` | Приглашения: персональные одноразовые и многоразовые ссылки отделов |
| `roles`, `permissions`, `role_permissions`, `user_roles` | Роли, права и области видимости |
| `delegations` | Передача прав ассистенту на срок |
| `working_hours` | Рабочие часы по дням недели, обед, буфер, разрешение поздних встреч |
| `availability_states` | Текущий индикатор доступности (одна строка на человека) |
| `availability_log` | История переключений — из неё считается реальная доступность |
| `calendar_blocks` | Личные блокировки «не занимать» |
| `absences` | Отпуска, командировки, больничные + замещающий |
| `holidays` | Праздники и перенесённые рабочие дни |
| `audit_log` | Журнал: только добавление, поля «было/стало», настоящий автор |

Блок 2 — поручения:

| Таблица | Назначение |
|---|---|
| `tasks` | Центральный объект. `escalation_level` хранит пройденную ступень эскалации, `extensions_count` — номер продления (входит в ключи уведомлений) |
| `task_events` | История: кто, что и когда изменил |
| `task_comments` | Обсуждение и файлы внутри поручения |
| `task_extensions` | Запросы на перенос срока. Частичный уникальный индекс: один открытый запрос на поручение |
| `task_templates` | Типовые поручения (интерфейса пока нет) |
| `notifications` | Очередь. `event_key` уникален — защита от дублей в схеме; `next_attempt_at` — откат при сбоях |
| `error_log` | Что сломалось: тип, сообщение, трассировка, действие человека. Показывается на `/health` |

Блоки 3 и 4 — календарь, встречи, решения, документы:

| Таблица | Назначение |
|---|---|
| `meetings` | Встречи. Пересечения у владельца запрещены схемой; `reschedule_count` входит в ключи уведомлений |
| `meeting_participants` | Кто зван. `UNIQUE (meeting_id, user_id)` |
| `meeting_requests` | Заявка на встречу до решения владельца календаря |
| `meeting_attendance` | Явка и опоздание в минутах. Одна отметка на человека |
| `meeting_ratings` | Оценка пользы встречи. Одна от человека |
| `slot_holds` | Резерв окна на время рассмотрения заявки. Освобождается фоновым циклом |
| `time_quotas` | Норма времени на отдел или человека. Личная сильнее отдельской |
| `rooms`, `room_bookings` | Переговорные. Модель готова, интерфейса нет |
| `agenda_items` | Повестка встречи, порядок задан полем, а не временем |
| `decisions` | Реестр решений. Живёт дольше встречи, связь с ней необязательна |
| `documents` | Идентификатор файла в Telegram, политика доступа, состояние разбора |
| `document_texts` | Извлечённый текст и хранимый `tsvector`. Отдельно от документа: он читается часто, текст тяжёлый |
| `document_access` | Кому и каким отделам открыт файл |
| `document_views` | Журнал открытий: обойти его другим путём нельзя |
| `download_tokens` | Одноразовые ссылки на файл |

Запланировано (блоки 5–6): `notification_templates`, `notification_prefs`,
`approvals`, `polls`, `ai_jobs`, `ai_budget`, `feature_flags`, `ui_config`,
`feedback`.

**Правила модели.** Все временные метки — `timestamptz` в UTC, показ в часовом
поясе пользователя. `telegram_user_id` — 64-битное целое. Значения перечислений
хранятся строками (читаемо в базе и в журнале).

**Правила живут в схеме, а не только в коде.** Уникальный `event_key`, частичный
уникальный индекс на открытые продления, `EXCLUDE USING gist` на пересечения
блокировок календаря — их нельзя обойти по забывчивости вызывающего кода.
Расширения `pg_trgm` и `btree_gist` включены, индексы под пересечение интервалов
для блока 3 созданы заранее.

**`organization_id` есть только там, где выборка идёт без якоря** —
в `notifications` и `audit_log`. Остальные таблицы выбираются по `user_id`
или `task_id`, которые организацию уже несут (решение Р-17).

## Права

Четыре уровня, работают одновременно:

1. **Роль** — кто ты. Шесть: `EXECUTIVE`, `ASSISTANT`, `DEPT_HEAD`, `EMPLOYEE`, `ADMIN`, `AUDITOR`.
2. **Право** — что тебе разрешено. 34 штуки, каталог в `app/services/rbac.py::PERMISSIONS`.
   Матрица ролей — 91 связка. Ни одного права вне каталога, ни одного невыданного.
3. **Область** — над какими записями: `SELF` → `SUBORDINATES` → `DEPARTMENT` → `ORGANIZATION`.
4. **Проверка записи** — `can_access_object()`: я автор? исполнитель? проверяющий? мой отдел?

Матрица ролей — `ROLE_MATRIX` в том же файле. Права загружаются функцией
`load_grants()`: собственные роли **плюс** действующие делегирования.

Повышенные роли перечислены в `ELEVATED_ROLES` — самостоятельно не выдаются.

## Индикатор доступности

Состояния: `OPEN` (принимаю), `BUSY` (занят), `DND` (не беспокоить),
`OFFLINE` (не выставлен, работают обычные правила календаря).

- У состояния всегда есть `until_at`; истёкшее показывается как `OFFLINE`
  без фонового задания — проверка происходит при чтении (`get_view`).
- Флаг `opens_late_slots` открывает окна после конца рабочего дня («поздний приём»).
- `visible_to_all` управляет тем, видят ли индикатор все сотрудники.
- Каждое переключение пишется в `availability_log` и в журнал аудита.

Рабочий день по умолчанию: **09:00–19:00**, обед 13:00–14:00, буфер 15 минут,
предел позднего приёма 22:00, суббота и воскресенье нерабочие.

## Порты

Стандартные порты на машине владельца заняты другими проектами, поэтому:
Postgres — `55432`, Redis — `56379`, API — `8010` (только на `127.0.0.1`).

## Поручения и контроль сроков

Переходы состояний собраны в `app/services/tasks.py` — обработчики статус
не меняют. Контроль сроков (`app/services/deadlines.py`) держится на трёх вещах:

1. **Ступень эскалации в поручении** — в установившемся состоянии проход
   планировщика не пишет в базу ничего.
2. **Ключ события с номером продления** — после продления повторная просрочка
   снова доходит до исполнителя.
3. **Порог «меньше или равно», а не окно** — простой обработчика не теряет
   напоминание, от повторов защищает `event_key`.

Доставка (`app/services/notifications.py`): восемь попыток с растущей паузой,
постоянные ошибки помечаются сразу, ограничение частоты Telegram откладывает
доставку не тратя попытку, большие пачки режутся по 15 сообщений и 3500 символов.

## Календарь: что решает схема, а что код

| Правило | Где живёт |
|---|---|
| Календарь владельца без пересечений | `EXCLUDE USING gist` на `meetings`, отменённые исключены |
| Одно действующее удержание окна | `EXCLUDE` на `slot_holds` с `released_at IS NULL` |
| Переговорная не бронируется дважды | `EXCLUDE` на `room_bookings` |
| Одна отметка явки на человека | `UNIQUE (meeting_id, user_id)` |
| Одна оценка встречи от человека | `UNIQUE (meeting_id, rated_by)` |

Проверка «свободно ли» в коде — подсказка, а не гарантия: между проверкой
и вставкой окно может занять другой. Поэтому каждая вставка идёт под точкой
сохранения, а отказ базы превращается в список свободных вариантов, а не
в сообщение об ошибке. Десять одновременных заявок на одно окно дают одно
удержание — это проверено прогоном через настоящий диспетчер.

## Права в двух видах: по записи и в запросе

Каждое правило доступа существует дважды: как проверка одной записи (`may_read`,
`access_for`) и как условие SQL для списков и поиска (`visible_filter`). Иначе
никак: проверять права поштучно после `LIMIT` — значит показывать пустую
страницу вместо своих записей, а показанное имя чужого документа уже
разглашение.

Два описания одного правила расходятся молча. Поэтому совпадение проверяется
прогоном по матрице «запись × человек»: для документов, поручений и решений —
в `smoke_block4.py`, для встреч — в `smoke_block3.py`. Это единственная защита,
которая не зависит от аккуратности при следующей правке.

**Условие запроса не заменяет проверку записи.** Обработчик, открывающий одну
запись по номеру из нажатой кнопки, обязан спросить `may_read`. Совпадение
организации доступа не даёт: у рядового сотрудника область права — «только
свои», и без третьего шага карточка отдавала бы чужое. Проверка выборкой
(«загрузим список и посмотрим, есть ли он там») тоже не годится: она врёт,
как только записей становится больше, чем `LIMIT`.

## Текст от человека нигде не становится кодом

Правило `esc()` для сообщений — частный случай общего: текст, введённый
человеком, не должен превращаться в разметку, формулу или команду ни в одном
формате, куда система его выкладывает.

| Формат | Что делает текст | Чем закрыто |
|---|---|---|
| Сообщение Telegram (HTML) | `<b>` в названии ломает доставку **всем** | `esc()` перед вставкой, порядок `esc(cut(x))` |
| Выгрузка Excel | строка с `=` становится формулой у того, кто откроет отчёт | `export._append_as_text`: тип ячейки строковый плюс `quotePrefix` |
| Выгрузка PDF | ничего: PDF не исполняет содержимое | — |

Порядок `esc(cut(x))`, а не наоборот: обрезка по числу знаков не знает про
сущности и режет `&lt;` пополам. Сообщение с половиной сущности Telegram
не доставляет.

## Соединения размножают строки

`outerjoin` по дочерней таблице возвращает родителя по разу на каждого потомка:
встреча с тремя участниками приходит тремя строками. Там, где результат
складывается или считается, это меняет ответ. Разбор такого запроса обязан
дедуплицировать по ключу — либо запрос обязан нести `distinct`.

Так `slots._load` однажды отдавал одну встречу трижды, счётчик «встреч подряд»
читал её как цепочку из трёх, и свободные окна пропадали из выдачи без
объяснения. Проверки этого не видели: они создавали встречи без участников.

| Правило | Где живёт |
|---|---|
| Карточка встречи открыта участнику, ведущему или области права | `meetings.may_read` + `visible_filter` |
| Решение открыто автору, ответственному или области права | `decisions.may_read` + `visible_filter` |
| Доступ к встрече не даёт доступа к её документам | `documents.may_read` + `visible_filter`, политика в `documents.scope` |
| Круг «участники» не открывается по должности | `BROAD_SCOPES` — в него входят только ORGANIZATION и DEPARTMENT |
| Каждое открытие файла в журнале | `documents.open_for` — проверка прав и запись в одной функции |
| Решение не удаляется | `decisions.close` — только DONE или CANCELLED с причиной |
| Закрыть можно только открытое тебе решение | `decisions.close` → `decisions.may_read` |

## Состояние системы

`/health` — один адрес для человека и для монитора: браузер получает страницу,
монитор получает JSON, код 503 в обоих случаях при неполадке.

Живость служб определяется отметками в Redis (`hb:bot`, `hb:worker:delivery`,
`hb:worker:deadlines`, `hb:worker:meetings`, `hb:worker:documents`): процесс
обновляет свою каждые 30 секунд, срок жизни 90.
«Контейнер запущен» и «служба работает» — разные вещи.

Неперехваченные ошибки бота (`dp.errors`) и сбои фоновых циклов пишутся
в `error_log` отдельной транзакцией: ошибка часто случается там, где основная
транзакция уже откатывается, и запись о ней должна это пережить.

**Обработчики получают бота параметром, а не импортом.** Глобальный
`app.bot.loader.bot` держит боевой токен: обработчик, взявший его напрямую,
отправит настоящее сообщение даже из проверочного прогона. Это уже случалось —
см. HISTORY.md, инцидент от 1 сентября. Правило закреплено проверкой
в `smoke_hardening.py`.

## Показатели

Пятнадцать метрик раздела 14 архитектуры живут в `app/services/analytics.py`.
Два правила, без которых им нельзя верить.

**Считает база.** Одна метрика — один агрегирующий запрос. Собирать пятнадцать
показателей по всей организации выборкой строк и сложением в Python — значит
положить бота на первой же тысяче поручений.

**Нет данных — это не ноль, и различает их знаменатель.** Нет отметок явки —
делить не на что, показателя не существует. Есть рабочие часы, но нет встреч —
знаменатель настоящий, и ноль настоящий. Поэтому загрузка календаря без встреч
показывает 0%, а без заданных рабочих часов молчит.

**Область считается по правам смотрящего** (`analytics.audience_for`):
`analytics.read_org` — организация, `analytics.read` с областью DEPARTMENT —
свой отдел и вложенные, рядовой сотрудник аналитику не получает вовсе.
Показатель, посчитанный шире, чем человеку открыто, — утечка в виде среднего.
