# Соглашения по коду

## Язык

- Комментарии, тексты интерфейса, документация — **русский**.
- Имена переменных, функций, таблиц, полей — **английский**.
- Тексты для пользователя не пишутся внутри бизнес-логики: только в обработчиках
  бота или в шаблонах уведомлений. К блоку 5 — через ключи переводов.

## Python

- Python 3.13, полные аннотации типов, современный синтаксис (`str | None`, `StrEnum`).
- Асинхронность везде: `async def`, `AsyncSession`, `redis.asyncio`.
- SQLAlchemy 2.0: `Mapped[...]` + `mapped_column(...)`, запросы через `select()`.
- Одна транзакция на действие: `async with session_scope() as session`.
  Коммит при успехе, откат при любой ошибке — вручную коммит не вызывать.
- Импорты: стандартная библиотека → сторонние → `app.*`, между группами пустая строка.

## Комментарии

Пиши комментарий там, где решение неочевидно, и объясняй **почему**, а не что.

```python
# Многоразовую ссылку отдела могут переслать кому угодно,
# поэтому повышенные роли через неё не выдаются никогда.
auto_approve = invite is not None and (...)
```

Не пиши комментарии, пересказывающие код (`# создаём пользователя` над `User(...)`).

## Модели

- Каждая таблица наследует `Base, PKMixin, TimestampMixin` (кроме журналов —
  им нужен только `created_at`).
- Время — `DateTime(timezone=True)`, хранение в UTC.
- Перечисления — строковые (`String(20)` + значение из `StrEnum`), не `Enum` Postgres:
  добавление нового значения не требует миграции типа.
- Внешние ключи всегда с `ondelete`: `CASCADE` для зависимых, `SET NULL` для ссылок.

## Права

Любой новый обработчик, показывающий или меняющий данные, обязан:

1. получить `grants` из middleware;
2. проверить право: `has_permission(grants, "task.read")`;
3. для конкретной записи вызвать `can_access_object(...)`.

Пропуск третьего шага — самая частая уязвимость такого класса систем.

## Журнал аудита

Критичные действия пишутся через `write_audit()` **в той же транзакции**,
что и само изменение. Обязательно для: изменения сроков, ролей, прав,
переносов, удалений, действий по делегированию, переключения доступности.

## Миграции

- Схема меняется только через Alembic. Ручные правки базы запрещены.
- Порядок безопасного изменения: добавить новое → обновить код → перенести данные →
  удалить старое отдельным релизом.
- После правки моделей: `alembic revision --autogenerate -m "описание"`,
  затем **прочитать сгенерированный файл** — автогенерация ошибается на индексах и типах.

## Бот

- Обработчики короткие: логика живёт в `app/services/`, обработчик только собирает
  ответ и клавиатуру.
- Каждое действие пользователя даёт понятный результат: что произошло, что изменилось,
  что делать дальше. Не `HTTP 409`, а «Это время уже занято. Свободны: 10:30, 11:00».
- Не больше 5–7 кнопок на экран. Тексты без технических терминов.
- Ошибки ловятся: недоступность Telegram (заблокировал бота) не должна ронять обработку.

## Проверки

Каждый блок заканчивается скриптом `scripts/smoke_block<N>.py`, который прогоняет
сценарий по реальной базе и печатает `Пройдено / Ошибок`. Скрипт обязан:

- убирать за собой тестовые данные (по диапазону `telegram_user_id >= 900_000_000`);
- проверять не только успешный путь, но и **отказы**: чужие данные, повышение прав,
  пересланные ссылки;
- завершаться ненулевым кодом при ошибке.

## Секреты

`.env` и только `.env`. В репозиторий не попадает (см. `.gitignore`), в образ не
копируется (см. `.dockerignore`), в переписку не пересылается.
