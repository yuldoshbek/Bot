# Соглашения по коду

## Язык

- Комментарии, тексты интерфейса, документация — **русский**.
- Имена переменных, функций, таблиц, полей — **английский**.
- Тексты для пользователя не пишутся внутри бизнес-логики: только в обработчиках
  бота или в шаблонах уведомлений. К блоку 5 — через ключи переводов.

## Python

- Python 3.13, полные аннотации типов, современный синтаксис (`str | None`, `StrEnum`).
- Асинхронность везде: `async def`, `AsyncSession`, `redis.asyncio`.
- SQLAlchemy 2.0: `Mapped[...]` + `mapped_column(...)`, запросы через `select()`.
- Одна транзакция на действие: `async with session_scope() as session`.
  Коммит при успехе, откат при любой ошибке — вручную коммит не вызывать.
- Импорты: стандартная библиотека → сторонние → `app.*`, между группами пустая строка.

## Комментарии

Пиши комментарий там, где решение неочевидно, и объясняй **почему**, а не что.

```python
# Многоразовую ссылку отдела могут переслать кому угодно,
# поэтому повышенные роли через неё не выдаются никогда.
auto_approve = invite is not None and (...)
```

Не пиши комментарии, пересказывающие код (`# создаём пользователя` над `User(...)`).

## Модели

- Каждая таблица наследует `Base, PKMixin, TimestampMixin` (кроме журналов —
  им нужен только `created_at`).
- Время — `DateTime(timezone=True)`, хранение в UTC.
- Перечисления — строковые (`String(20)` + значение из `StrEnum`), не `Enum` Postgres:
  добавление нового значения не требует миграции типа.
- Внешние ключи всегда с `ondelete`: `CASCADE` для зависимых, `SET NULL` для ссылок.

## Права

Любой новый обработчик, показывающий или меняющий данные, обязан:

1. получить `grants` из middleware;
2. проверить право: `has_permission(grants, "task.read")`;
3. для конкретной записи вызвать `can_access_object(...)`.

Пропуск третьего шага — самая частая уязвимость такого класса систем.

## Журнал аудита

Критичные действия пишутся через `write_audit()` **в той же транзакции**,
что и само изменение. Обязательно для: изменения сроков, ролей, прав,
переносов, удалений, действий по делегированию, переключения доступности.

## Миграции

- Схема меняется только через Alembic. Ручные правки базы запрещены.
- Порядок безопасного изменения: добавить новое → обновить код → перенести данные →
  удалить старое отдельным релизом.
- После правки моделей: `alembic revision --autogenerate -m "описание"`,
  затем **прочитать сгенерированный файл** — автогенерация ошибается на индексах и типах.

## Бот

- Обработчики короткие: логика живёт в `app/services/`, обработчик только собирает
  ответ и клавиатуру.
- Каждое действие пользователя даёт понятный результат: что произошло, что изменилось,
  что делать дальше. Не `HTTP 409`, а «Это время уже занято. Свободны: 10:30, 11:00».
- Не больше 5–7 кнопок на экран. Тексты без технических терминов.
- Ошибки ловятся: недоступность Telegram (заблокировал бота) не должна ронять обработку.

## Проверки

Каждый блок заканчивается скриптом `scripts/smoke_block<N>.py`, который прогоняет
сценарий по реальной базе и печатает `Пройдено / Ошибок`. Скрипт обязан:

- **создавать все данные внутри организации с названием `ТЕСТ ...` и удалять
  строго по `organization_id`**;
- **падать до исправления.** Проверка, которая проходит и с ошибкой, и без неё,
  не проверяет ничего. Новый сценарий обязательно прогоняется на откаченном
  исправлении: на этом проекте фальшивой оказалась проверка индексов —
  «или индекс, или Seq Scan» верно при любом исходе;
- **создавать данные так, как их создаёт живая система.** Встреча без строк
  участников не встреча: именно поэтому дубли в расчёте окон прожили два блока
  незамеченными;
- проверять не только успешный путь, но и **отказы**: чужие данные, повышение прав,
  пересланные ссылки;
- заканчиваться проверкой, что боевые записи на месте;
- завершаться ненулевым кодом при ошибке.

> **Никогда не удаляй тестовые данные по диапазону `telegram_user_id`.** Реальный
> идентификатор сотрудника может оказаться в любом числовом диапазоне: на этом
> проекте уборка «всё, что больше 900 000 000» однажды удалила боевого пользователя
> с ID 976130670. Признаком тестовых данных должна быть принадлежность к тестовой
> организации, а не форма идентификатора.

## Текст в сообщениях

Сообщения уходят в режиме HTML, и Telegram разбирает разметку строго: неизвестный
тег — сообщение не доходит **ни до кого**. Любой текст от человека (название
поручения, комментарий, ФИО, причина переноса, название отдела) перед вставкой
в сообщение пропускается через `esc()` из `app/core/text.py`.

```python
f"📋 <b>{esc(task.title)}</b>"   # правильно
f"📋 <b>{task.title}</b>"        # сломается на названии «Проверить <новый> регламент»
```

Собственная разметка (`<b>`, `<code>`) пишется в коде и экранированию не подлежит.
Текст в подписях кнопок не экранируется — там HTML не разбирается.

В базе текст хранится как есть: экранирование — свойство показа, а не данных.

## Тот же запрет в других форматах

`esc()` — частный случай правила «текст от человека нигде не становится кодом».
Появляется новый формат вывода — сразу спрашивай, что в нём делает текст,
начинающийся со служебного знака.

**Excel.** `openpyxl` пишет строку, начинающуюся с `=`, формулой. Поручение
с названием `=cmd|'/c calc'!A1` станет исполняемой ячейкой у того, кто откроет
отчёт. Строки пишутся через `export._append_as_text`, а не `page.append`
напрямую: тип ячейки принудительно строковый, плюс `quotePrefix`.

**Порядок обрезки.** Всегда `esc(cut(x))` и никогда `cut(esc(x))`: обрезка
считает знаки и не знает про сущности — `&lt;` разрубается пополам, и Telegram
не доставляет сообщение. Ловушка не в прямом вызове, а в сборке списка:

```python
names = ", ".join(esc(p.full_name) for p in people)   # неправильно
cut(names, 200)                                        # уже поздно

names = ", ".join(p.full_name for p in people)        # правильно
esc(cut(names, 200))
```

## Проверки на прочность

Кроме сценарных проверок каждый блок проходит `scripts/stress_test.py`. Он прогоняет
настоящие обновления через настоящий диспетчер и бьёт по системе так, как это делает
живой человек с нервами:

- одна кнопка нажата десять раз подряд и десять раз одновременно;
- чужой человек жмёт кнопки чужой записи;
- в callback подставлены чужие и несуществующие идентификаторы;
- в поля введены HTML, эмодзи, 5000 символов, попытка SQL-инъекции, кривые даты.

Новый обработчик должен пережить всё это, не уронив бота и не оставив человека
без ответа. Правила, которые из этого следуют:

- **никогда `int()` от данных кнопки** — только `callback_int()`, который вернёт `None`;
- **повторное действие не должно дублировать запись** — переход проверяет текущий статус;
- **один открытый запрос на объект** — десять нажатий «Продлить» дают один запрос, а не десять;
- **проверка обязана падать оценкой, а не исключением.** Обращение по ключу
  к полю, которого может не быть, роняет весь набор, и всё после этой строки
  не выполняется — на экране это выглядит как «прошло». Разбор ответа идёт
  через `.get`, а не по ключу;
- **проверка на прочность обязана считать записи, а не только ловить исключения.**
  «Обработчик не упал» — половина ответа: десять нажатий «Сохранить как шаблон»
  не падали и заводили десять шаблонов. Рядом с каждой проверкой «не уронило
  бота» стоит вторая — сколько записей после этого в базе.

Где создание не защищено переходом состояния (у новой записи статуса ещё нет),
признаком двойного нажатия служит пара «то же самое» плюс **свежесть**. Один
статус недостаточен: еженедельная задача, выданная в прошлый понедельник и
так и не принятая, не делает сегодняшнюю дубликатом.

## Права: что именно передавать третьим шагом

Правило «grants → has_permission → can_access_object» соблюдается формально, если
третий шаг подменить самодельной проверкой в обработчике. Проверяемая формулировка:

> **В обработчике не должно быть сравнений вида `task.assignee_id == user.id`.**
> Отношение к записи определяет только `can_access_object` или `access_for`.

Наличие права никогда не равно возможности действовать над записью. Особенно это
касается создания: право `task.create` есть и у рядового сотрудника — с областью
«только свои». Без проверки области он назначит поручение руководителю.

Идентификатор, пришедший из нажатой кнопки, проверяется заново **всегда**, включая
принадлежность к организации: `adm:approve:<чужой id>` не должен сработать.

**Правило распространяется и на чтение.** Обработчик, который просто показывает
карточку, — то же самое место утечки, что и обработчик, который меняет данные:
показанные тема встречи, состав участников и имя чужого файла уже разглашение.
Совпадения организации мало, потому что область права у рядового сотрудника —
«только свои». Карточка встречи однажды отдавала любую встречу организации
именно потому, что проверка сводилась к `meeting.organization_id == user.organization_id`.

Проверять доступ выборкой («загрузим список видимого и посмотрим, есть ли он
там») тоже нельзя: такая проверка врёт, как только записей больше, чем `LIMIT`.
Для одной записи нужна парная функция — `may_read` / `access_for`.

## Запросы: ни одного обращения к базе внутри цикла

Данные для всей выборки грузятся одним запросом с `IN`, дальше сопоставляются
в Python (`deadlines._load_people` — образец). Без этого правила блок 3 (участники
встречи) и блок 5 (пятнадцать показателей дашборда) повторят проблему в удвоенном
объёме: пятнадцать `COUNT(*)` на каждое открытие экрана.

## Соединение размножает строки

`outerjoin` по дочерней таблице возвращает родителя по разу на каждого потомка.
Встреча с тремя участниками приходит тремя строками, и разбор, который просто
складывает всё подряд в список, получает три встречи вместо одной. На занятость
это не влияет — интервалы схлопываются, — но всё, что **считает**, начинает врать.

Поэтому: либо `distinct` в запросе, либо дедупликация по ключу при разборе.

```python
for meeting, participant_id in rows:
    if (person_id, meeting.id) in seen:   # обязательно
        continue
```

Так `slots._load` отдавал одну встречу трижды, счётчик «встреч подряд» считал её
цепочкой из трёх, и свободные окна исчезали из выдачи молча.

## Секреты

`.env` и только `.env`. В репозиторий не попадает (см. `.gitignore`), в образ не
копируется (см. `.dockerignore`), в переписку не пересылается.

## Язык интерфейса: ключ, а не строка

`t("menu.tasks", locale)`, а не `"📋 Мои поручения"`. Строка как ключ выглядит
удобной ровно до первой правки формулировки: поправил текст — потерял все переводы.

Эталон — **узбекская латиница** (`app/i18n/uz.py`). Ключа, которого нет в ней,
не существует; отдельная проверка это стережёт. Русский может отставать, и тогда
человек увидит узбекскую строку: хуже перевода, но лучше пустоты или имени ключа
на экране.

**Кириллица не набирается руками.** Она выводится из латиницы правилом
(`app/core/translit.py`). Полторы тысячи строк, набранных дважды, разошлись бы
на первой правке. Где правило врёт — короткая таблица исключений
(`app/i18n/uz_cyrl.py`), а не отказ от правила. Список исключений, который растёт,
означает, что чинить надо правило.

## Понимать все языки, говорить на одном

Разбор ввода принимает **все языки сразу** и не смотрит на настройку человека:
в узбекском кабинете «juma gacha» и «до пятницы» пишет один и тот же человек
в течение одного дня. Срок, не понятый из-за настройки в профиле, выглядит
поломкой системы, а не следствием выбора языка.

Ответ, наоборот, строго на языке собеседника. И **на языке получателя, а не
отправителя**: рассылка нескольким людям собирается внутри цикла, по разу
на каждого. Один текст на всех показал бы половине из них чужой язык.

```python
for admin in admins:                      # текст внутри цикла
    text = t("start.new_application", admin.locale)
```

## Кнопка нижнего меню — это текст сообщения

Telegram присылает не код кнопки, а её надпись, и обработчик ловит её сравнением
строк. Как только надписи стали переводиться, сравнение с одной строкой сломалось.

Отсюда `MenuButton(MENU_PROFILE)`: фильтр сверяет надпись **со всеми** переводами
ключа. Это же решает вторую задачу — Telegram не обновляет клавиатуру, уже лежащую
в чате, и после смены языка человек какое-то время жмёт старые кнопки.

Следствие: две кнопки не должны совпадать надписью ни на одном языке, иначе одно
нажатие запустит два обработчика. Проверка на это есть.

## Проверка, приведённая к допустимому, ничего не проверяет

```python
code = normalize(call.data.split(":", 1)[1])
if code not in LOCALES:      # никогда не сработает
```

`normalize` возвращает основной язык на что угодно, поэтому проверять им же
приведённое значение бессмысленно: `lang:menu` прошёл бы как `uz` и молча сменил
человеку язык. Сверять надо **присланное**, а приводить — уже принятое.

## Падающая проверка прячет следующие за ней

Проверка, которая не сравнивает, а падает, обрывает весь раздел, и всё, что за
ней, выглядит пройденным. Если проверяемый вызов **может** возбудить исключение —
а проверка на то и стоит, что может, — вызов заворачивается:

```python
def said(key, locale=None, **params):
    try:
        return t(key, locale, **params)
    except Exception:
        return None          # None означает «упало», а не «пусто»
```

Так же читаются словари и JSON: `.get`, а не `[...]`.

## `LIMIT` без `ORDER BY` — это «любая строка», а не «первая»

PostgreSQL без сортировки отдаёт строку в том порядке, в каком она лежит
физически, и порядок меняется от того, что происходило с таблицей раньше.
В проверках это выглядит как случайное падение: один и тот же набор проходит
в одиночку и падает следом за другими.

Так проверка шаблонов выбирала исходное поручение и то считала его вместе
с созданными, то нет.

## Гонка за отсутствие записи

`with_for_update` запирает существующую строку. Когда две транзакции спорят
за то, что записи **нет** — «проверил, что близнеца нет, и создал», — запирать
нечего: ни одна не видит незакоммиченную запись другой, обе проходят проверку,
обе создают.

Ответ PostgreSQL — рекомендательная блокировка: замок на значении, которого ещё
нет. Держится до конца транзакции, снимается сама при фиксации и откате.

```python
await session.execute(
    text("SELECT pg_advisory_xact_lock(:key)"),
    {"key": (template.id << 32) | (target.id & 0xFFFFFFFF)},
)
```

Ключ собирается из чисел, а не из хеша строки: `hash()` в Python разный от
запуска к запуску, и замок в двух процессах оказался бы разным.

## Десять вызовов подряд — не десять одновременных

Цикл из десяти `await` идёт строго по очереди и гонку не воспроизводит вовсе.
Проверка «десять нажатий подряд» молча подтвердит защиту, которой нет.
Одновременность проверяется одновременностью — `asyncio.gather` с отдельной
транзакцией на каждый вызов. В шаблонах разница оказалась ровно такой:
последовательно — одно поручение, параллельно — девять.
